# 设计 Skill 展示站优化方案

核验日期：2026-10-31

评审基线：`site/showcase`，提交 `d5ce14aff7186c60c16e8765a86079ee1e208b99`，已在前一阶段核对为当前 Vercel 生产部署对应提交

本轮范围是当前源码、已构建 HTML、CSS 与实验数据的结构评审。浏览器工具在会话中更新，后续返回「Local browser use is disabled in Work settings」，未完成本轮桌面/手机截图与交互验证，因此本文不对实际渲染、性能或无障碍合规给出通过结论

## 建议的核心调整

网站首先帮助读者回答「这几个 Skill 差在哪里，我这个任务先试谁」，然后提供真实产物与实验记录来核对判断

现有源码更突出实验批次和执行开销。V2/V3 继续保留为证据维度，首页的主要组织方式改为 Skill 与使用任务

## 当前路径检查

| 步骤 | 当前结构及状态 | 依据 |
| --- | --- | --- |
| 1. 进入首页 | 设定交代完整，但主标题、对照说明、版本切换、会话总量都出现在成果列表之前；缺少选型入口 | `site/build.mjs` 的 `buildIndex()`、`buildEditionPanel()` |
| 2. 浏览某个 Skill | 有预览图和数据，缺少特点、推荐任务、使用取舍与原始资料入口 | 卡片模板主要输出名称、耗时、LLM/工具调用和是否读取 Skill |
| 3. 打开详情 | 有同一 Skill 的版本比较；没有不同 Skill 的同版本比较；20 个版本跑次均没有非空 review.md | `buildCompareDetail()`、`buildCompareColumn()` 与当前文件检查 |
| 4. 窄屏比较 | 源码在 900px 以下改为单列，且两版各自包含完整的统计、预览、截图、数据和评价，需重点验证跨长页对照的负担 | `site/style.css:1139`；此处为结构风险，未在手机上实测 |

## 第一优先级：补齐选型信息，修正数据表达

首页标题建议：**设计 Skill 怎么选？先看同题做出的页面**

副文案说明「9 个设计项目 + 1 个裸 Pi 对照，使用同一份个人页资料」，再用一行交代模型与实验时间。保留「仅个人页实测，其他任务建议来自作者文档」的边界

首页先放任务入口，例如个人站/作品集、营销落地页、后台与产品界面、原型与演示、已有风格参考。同一个 Skill 可以属于多个任务，标签只代表文档定位，不冒充跨场景实测结果

卡片至少包含：

- 成果预览与 Skill 名称
- 一句具体特点
- 适合优先试的任务
- 一项主要取舍
- 查看实测与原始资料入口

耗时、调用数继续保留，但退到次要位置。不要按调用数默认排序，让访客误把执行成本当成设计质量

内容可以沿用知识库中已经整理的九项目资料。实现时把「作者文档描述」「本次个人页观察」「编辑建议」分字段保存，新增建议仍保留待确认状态，不自动冒充 Chasen 已确认的实测评价

同时修正以下已核实的问题：

| 当前表达 | 调整建议 | 依据 |
| --- | --- | --- |
| 10 个设计 skill | 9 个设计项目 + 1 个裸对照 | 00-bare 没装 Skill；09 只采用了一份 DESIGN.md |
| 总耗时 | 各组耗时累计，并说明不是整批实际经过时间 | `totals.duration` 对各跑次 duration 求和 |
| V3 一次成版 | 一次成版要求，或限制迭代版；展开说明实际执行情况 | V3 部分组仍有多次修改，06 组仍有浏览器相关检查 |
| V3 裸对照显示读了 Skill | 显示未安装 / 不适用，另注分析器误标 | `_analysis.md` 明确解释该组仅探测文件名，`read_skill` 被误标为 true；当前模板直接读取布尔值 |
| 输入 token 绝大部分是缓存命中 | 分别解释 provider 的 input 与 cacheRead 字段，不根据这句话换算成本 | 页面表格本已分别列出字段，当前说明容易让两列关系变得含糊 |

保留 taste-skill 中断提示，不把有 HTML 与截图等同于正常完成验收

## 第二优先级：增加真正服务选型的比较方式

目前解决的是「同一个 Skill，V2 和 V3 有何差异」。用户还需要「同一批次下，不同 Skill 有何差异」

建议先提供最多 2–3 个候选的横向比较，固定同一实验版本和截图规格。一次不让所有页面都挤进屏幕

对比时先看成果截图和特点、适用任务、主要取舍，再看执行数据。不要自动生成综合分或最佳榜单，已有数据并不支持这种强结论

将两种比较清楚命名：

- **比较不同 Skill**：同批次的候选横向看
- **查看两次实验**：同一 Skill 的 V2/V3 看变化

选择状态写进 URL，使候选、版本能够分享，并让返回总览时保留上次状态。当前首页虽支持版本 hash，但详情页返回的是没有版本 hash 的 index.html

## 第三优先级：重排详情页，减少来回翻找

详情页建议按下面的顺序组织：

1. 这个 Skill 提供什么、适合先试什么、主要取舍
2. 成果截图与版本切换
3. 本次可观察的差异、亮点与不足
4. 独立打开的交互预览
5. 执行数据、提示词与原始证据

当前每一版都完整重复「说明→数字→缩略图→iframe→全页截图→数据→评价」，两版的相同维度距离很远。建议改为按维度组织，把对应内容放在一起

实际 iframe 宽度跟随比较栏变化，生成页面可能因此进入不同响应式断点。用它观察操作行为可以，但不宜把窄栏预览直接当成原桌面截图的版式证据。默认展示固定规格截图，交互预览单独打开，并说明视口尺寸

手机端优先采用同位置切换 V2/V3，或同一维度内切换候选，避免看完一整版所有材料后才能看到另一版。此建议需在实施后用真实手机宽度验证

移除产品页面里的「编辑 runs/.../review.md 后重新构建即可更新」等维护说明，放回项目文档；已有评价缺失时先处理内容状态，不让整站每组都以占位文字结束

## 视觉与可访问性处理顺序

先保留现有米白底、橙色强调和字体体系，避免在内容架构未定时重画整站

随后再根据新页面截图处理信息层级：成果预览、Skill 名和一句特点承担主信息；重复实验标签、长路径和执行指标降低强调。表格、长 Prompt 和日志默认折叠，保持可访问的展开入口

源码已有跳转主内容链接、focus-visible、图片 alt、iframe title 和减少动效分支，这些需要保留。后续用键盘核验筛选、候选选择、版本切换的焦点顺序与状态通知；检查触控目标、正文对比度、缩放与溢出。没有做过这些检查之前，不写「无障碍已通过」

## 最小实施范围

第一轮只做「首页内容重排 + 九项目简介 + 数据文案修正 + 详情摘要」，保留现有构建器、实验目录、原始产物和部署流程

第二轮再做「2–3 个候选比较 + 可分享状态 + 窄屏比较方式」。不引入账号、数据库、投票、打分、评论或新的前端框架

实施完成后的验收目标：

- 访客不先理解 V2/V3，也能从任务入口找到候选
- 每个项目都有可核对来源的特点与取舍
- 可在同一批次和相同截图规格下比较至少两个 Skill
- 实测结论与文档定位明确区分
- 实验设置、Prompt、日志和原始页面仍能找到
- 390px、768px 和桌面宽度下实际浏览、切换和返回路径可用

本轮仅新增此方案，没有修改网站代码或部署内容
